# Master PRD — College Event Kit Relay

**Status:** Draft v1.0
**Owner:** Platform / Backend
**Last updated:** 2026-10-10

---

## 1. Summary

College Event Kit Relay is a reservation and custody-tracking system for shared
audio-visual **EventKits** (camera, mic, tripod, light). A single physical kit is
reserved by many college clubs across sequential time slots. Between any two
consecutive reservations the kit must pass a mandatory **15-minute inspection
window**. Late returns shift the next club's *effective* start time while the
*original* booking is preserved, and delays cascade forward through the schedule.

The core mental model is a **relay timeline**: the kit is one shared resource
moving through an ordered sequence of reservations, not an independent booking
per club.

## 2. Goals

- Let clubs reserve a kit for a time slot and receive it only when it is complete, usable, and free.
- Enforce the 15-minute turnaround inspection between every pair of reservations.
- Handle late returns by recomputing effective start times and cascading the delay.
- Detect damage during inspection and resolve it via replace → reroute → cancel.
- Auto-expire reservations left **PENDING** past their hold deadline and auto-flag **NO_SHOW** confirmations.
- Track custody so damage is attributed to the club that held the kit, never the next one.
- Manage security deposits and a loyalty score that gates eligibility.
- Notify affected clubs and organizers on every exception (delay, damage, reroute, cancel, expiry).

## 3. Non-goals (v1)

- Payment gateway integration (deposit is modeled as hold/refund/forfeit state only).
- Multi-campus / multi-region distribution (single-process locking assumed).
- Mobile apps (responsive web only).
- Real-time websockets (polling + scheduled sweeps are sufficient for v1).

## 4. Personas

| Persona | Needs |
|---------|-------|
| **Club** (customer) | Reserve a kit, confirm within the hold window, check out, return on time, keep loyalty up. |
| **Organizer** (admin) | Inspect returned kits, record damage, replace equipment, reroute/cancel, warn clubs. |

## 6. Domain glossary

| Term | Meaning |

| Reservation | One club's booking of one kit for a time slot. |
| booked_slot | Original intent — never mutated. |
| effective_slot | Operational schedule — shifts with real delays. |
| TurnaroundWindow | Mandatory 15-minute inspection gap between reservations. |
| KitSchedule | Ordered relay timeline of reservations for one kit. |
| Inspection | Condition check performed inside the turnaround window. |
| Handover | Recorded physical transfer (CHECKOUT or RETURN). |
| KitCondition | Snapshot of every item's status at a handover (audit). |
| Deposit | Security hold tied to a reservation. |
| Hold (soft hold) | A PENDING reservation reserving the kit until its deadline. |

## 7. End-to-end flow

```
Club.requestReservation
      -> ReservationService.create (validators + specs, soft hold, deposit PENDING)
      -> confirm within hold window ................ else PENDING-expiry cron -> EXPIRED
      -> HandoverService.checkout (kit CHECKED_OUT)
      -> club uses kit
      -> HandoverService.return_kit (kit AWAITING_INSPECTION, KitCondition recorded)
      -> InspectionService 15-min window
            PASS -> kit AVAILABLE -> propagate_delay -> notify next club
            FAIL -> replace (spare) | reroute (another kit) | cancel
      -> DepositPolicy.settle, LoyaltyPolicy applied via event subscribers
```

## 9. Core business rules (authoritative)

1. A damaged or incomplete kit cannot be reserved.
2. A kit cannot be checked out before its reservation is CONFIRMED.
3. Every returned kit must go through inspection.
4. The inspection window is exactly 15 minutes (configurable via `HoldPolicy`/`TurnaroundWindow`).
5. The next club receives the kit only after inspection completes successfully.
6. A late return shifts the next club's effective start time.
7. Delay propagates to subsequent reservations.
8. Original reservation times are preserved.
9. Effective operational times reflect actual delays.
10. Damage is attributed by custody — the next club is never blamed.
11. Damaged equipment is replaced when a spare exists.
12. If replacement is impossible, reroute the reservation to another suitable kit.
13. If no suitable kit exists, cancel the reservation.
14. Notifications are sent on delay, damage, reroute, cancel, and expiry.
15. Deposits are refunded on a clean on-time return and forfeited (fully or partially) otherwise.
16. **(new)** A PENDING reservation is auto-rejected (**EXPIRED**) when its hold deadline passes.
17. **(new)** A CONFIRMED reservation that is never checked out past its grace is flagged **NO_SHOW**.

## 10. Success metrics

- 100% of returned kits pass through an inspection record before reuse.
- 0 double-bookings of the same kit/slot under concurrent requests.
- Pending holds expire within one sweep interval (≤ 60 s) of their deadline.
- Delay cascades computed deterministically (verified by unit tests with a FixedClock).

## 11. Milestones

1. **M1** — Scaffolding, DB schema, migrations, health check (this deliverable).
2. **M2** — Reservation create/confirm + validators + soft hold + deposit hold.
3. **M3** — Checkout/return handover + inspection window + state machine.
4. **M4** — Damage handling (replace/reroute/cancel) + delay propagation.
5. **M5** — Crons (pending-expiry, no-show) + notifications + loyalty.
6. **M6** — Frontend dashboards (organizer + club) + generated API client.

## 12. Risks

| Risk | Mitigation |
|------|-----------|
| Race between confirm and pending-expiry | Per-kit lock + status re-check + optimistic `version`. |
| Clock coupling makes sweeps untestable | `Clock` port + `FixedClock` in tests. |
| Cascading delay logic drift | Single `KitSchedule.propagate_delay` + golden unit tests. |
| Deposit/loyalty side effects coupling the relay | Domain events + subscribers (Observer). |
